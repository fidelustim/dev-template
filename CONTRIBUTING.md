# Как мы работаем с кодом

## Порядок работы над фичей

1. **Спецификация** — задача в трекере + `docs/spec/NNNN-<имя>.md` (цель, границы, критерии приёмки).
2. **Архитектура** — если фича затрагивает структуру системы: ADR в `docs/adr/`.
3. **Декомпозиция** — спек разбивается на подзадачи с зависимостями.
4. **Ветка** — `feature/<ID>-<имя>` от `develop`.
5. **Код + тесты** — вместе, не отдельными PR.
6. **PR → ревью** — обязательный чек-лист из шаблона PR. CI зелёный. Ревью второго агента/человека.
7. **Merge в `develop`** — squash, история линейная.
8. **Релиз** — `release/<версия>` → `main`, тег `vX.Y.Z`, changelog.

## Коммиты

Формат: `<тип>(<область>): <описание> [<ID задачи>]`

Типы: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `ci`.

Пример: `feat(auth): вход по токену [PROJ-14]`

## Контроль соблюдения процесса

Два барьера (подробности — ADR-0002):

1. **Хук `pre-push`** на сервере агентов (`~/.git-hooks/pre-push`, версия в `scripts/pre-push`). Прямой `git push` в `main`/`develop` отклоняется. Осознанный обход — только для релиза: `ALLOW_PROTECTED_PUSH=1 git push`.
2. **Workflow `Guard (gitflow)`** — если прямой пуш всё же прошёл (например, с другой машины), пуш помечается красным в Actions.

Бесплатный план GitHub не даёт branch protection на приватных репозиториях. Когда появится GitHub Pro — включить защиту: `scripts/setup-branch-protection.sh`.

В репозитории уже включены (это работает и на бесплатном плане): только squash-merge, запрет merge-коммитов и rebase, авто-удаление ветки после мерджа. Поэтому история в `develop` и `main` линейная.

Требование одобрения ревью (`REQUIRED_APPROVALS=1`) включать нельзя, пока в репозитории один аккаунт: GitHub запрещает одобрять собственный PR, и мерджи встанут.
